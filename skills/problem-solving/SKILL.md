# Problem Solving

用最短适用路径完成用户要的结果。自动选择本 Skill 时，以实际未知和取舍为信号，不因任务带有“复杂”“架构”等词就展开全部方法。用户显式调用时，简单任务仍直接完成。

## 通用主线：明确交付并验收

1. 从请求、已有对话和相关项目资料识别交付物、范围、硬约束、已授权动作与可观察的完成条件。清楚的小任务直接沿用原话，无需先输出计划或请用户确认。已有项目先复用架构、历史决定、已知限制与测试；只读相关部分。区分用户选定的要求与可调整的实现建议。
2. 问：**这项未知得到不同答案时，交付、行动或风险判断会变吗？** 不会则直接执行并检查。会则先解决其他决定依赖的那一项未知；已有材料够用就复用。不要机械走遍方法，不按复杂度标签强制展开研究。
3. 执行已请求且已授权的工作。研究交付报告，建议交付推荐，实现交付实际改动；不把建议任务扩成实施，也不把实施停在建议。对风险增加有关的验证，风险高低本身不替代授权判断。
4. 核对规格和实际用途：要求是否满足，用户能否从正常入口得到所需结果。简单任务一次检查即可；系统修改检查关键依赖、旧行为和代表性入口。未运行的检查只能标为待验证。关键验收通过、剩余未知不会改变处置时停止。

## 只加载需要的方法

| 决定下一步的信号 | 读取 | 回到主线的条件 |
| --- | --- | --- |
| 关键事实的来源、时效、版本或适用范围不足或冲突 | [证据核验](references/evidence-verification.md) | 依据足以支持当前决定，或缺口已明确 |
| 行为偏离预期，未知原因影响修法 | [假设驱动排障](references/hypothesis-troubleshooting.md) | 证据支持修复及复测，或准确说明受阻项 |
| 多个可行方案存在影响目标的实质取舍 | [方案权衡](references/solution-tradeoffs.md) | 推荐稳定，或给出条件式选择 |

多个方法可串联，但共享已有证据和验收记录。原因已可靠定位的小故障可直接修复。存在多个技术选项并不自动需要比较表。

复杂任务即使已有一种实现方法，也要先检查现有架构、依赖和可用能力，主动考虑是否有更合适的成熟库、框架、Skill、MCP 或开源方案。核实候选工具是否实际安装、连接及获准使用；仅对可能改变效果、兼容性、维护负担或行动的缺口查官方资料或做测试。已有方案足够好就停止，不为采用新技术增加复杂度。

### 共用动作：最小试验

任一分支遇到可测且会改变行动的未知，都可以使用：

**假设 → 能区分判断的检查与通过条件 → 代表性低成本样本 → 实际观察 → 下一步决定。**

先说明什么观察会改变行动。采用有权限、风险相称的检查，保留必要的恢复办法。模拟、原型和真实用户表现分别记录；不得用模拟代替真实参与者反馈。只有上一轮产生具体新疑问且再测会改变行动，才开始下一轮。详例见方案权衡参考的“共用动作”。

### 条件辅助：系统因果图

仅在**跨组件反复故障**中，普通排障无法解释复发，且反馈或延迟关系会改变修复点、监控或试验时补充。读取排障参考的条件辅助部分。图或短关系清单均可；每条关系附观察依据或明确标待验证。普通新功能、单点错误、一般架构建议不默认画图。

## 决定边界与提问

用户决定产品目标、个人偏好、体验、优先级、预算和授权。AI 负责专业研究、技术选择、实现和验证；在已知约束内自行选择框架、接口、存储和测试。技术选择若引入新的费用、产品承诺或权限范围，提取其中用户拥有的决定再问，不让用户替 AI 选技术。

先查已有材料和已表达的偏好。只有当前必须作出的用户专属决定仍缺失时，提出能区分路线的最小问题，说明结果影响，继续不依赖答案的工作。用户未答不代表授权；沿用已授权范围，不重复确认已决定事项。

本 Skill 补充已有专业工作流，不覆盖用户要求、权限或全局协作约定。不要修改全局配置、安装自身或进行未授权发布。

重大架构调整、重要决策及产品方向变化应及时沟通其影响；沟通不等于将技术选型转交用户，也不机械增加确认步骤。小幅歧义可依据上下文处理并说明假设。用户建议的方法明显不适合目标时，指出依据，比较替代方案的效果、成本和风险；涉及用户专属决定先征求意见。用户了解风险后坚持原方案时，在授权和可行范围内尊重决定。

## 交付与收敛

按任务大小简洁说明结果、依据和验证。涉及项目时解释系统层面的逻辑：输入怎样经过相关环节产生用户结果，改变哪一环、为何、对其他环节的影响；无需倾倒代码细节或内部思考过程。

说明主要模块及职责、选型理由、优点、局限、验证方式和后续可改进处，所有架构解释须来自实际文件和执行观察。重要架构变化及时更新现有运行说明（如 ARCHITECTURE.md）。按复杂度在开始、关键阶段和结束报告有价值的发现、决定或阻碍。

可靠性优先，区分三个完成层次：代码完成、功能验证、实际场景目标达成。基础检查覆盖主要路径及有关异常；重要功能、重大架构变化和高风险工作设专门验收标准并充分验证。代码写完不等于功能通过，功能通过不自动证明目标达成。

区分“实际观察/已验证”“基于证据的推断”“尚未验证”。实现说明改动和实际检查；研究给结论、可定位依据与范围；决策给推荐、取舍和改选条件。缺环境、材料或授权时完成独立部分，说明受影响的验收项和最小下一步，不宣称全部完成。

复杂任务只需保留必要的“目标与通过条件｜关键未知｜观察与决定｜验收状态”，证据记一次并复用。只有具体的新证据入口可能改变决定时才继续调查；验证失败只回到相关分支，避免无证据反复推理。

AI 承担任务范围内的版本管理、必要备份和维护。复杂任务结束时适度检查目标偏离、遗漏方案、重复操作、错误判断和验证不足；仅按实际案例及原因提出改进。当前问题直接修复，项目问题考虑项目规范，跨项目重复问题才建议全局规则调整；优先优化合并已有规则，未经用户同意不修改全局 AGENTS.md。没有实际改进点不强制写复盘。
